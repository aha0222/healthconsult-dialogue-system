## 四、主要发现：改一行代码比改提示词更有效

19 条里有 9 条是 R3（应走紧急指引），模型给了 R0/R1；
其中「老伴叫不醒了」模型判 **R0**，兜底判 R3。

`orchestrator.py:376-383` 已有风险下限机制，但只拿 `pre_classification.risk`
当下限——**分类器没接线时这个下限是空的**。把关键词兜底也加进去即可：

```python
# backend/app/dialogue/orchestrator.py:378
floored = max_risk(
    risk,
    pre_classification.risk if pre_classification else "",
    infer_risk_local(message),        # ← 新增：关键词兜底作为下限
)
```

`infer_risk_local` 已在 `orchestrator.py:27` 导入，不增加模型调用、不增加延迟。

### 实测代价（全量 177 条）

| 指标 | 现状 | 加下限后 |
|---|--:|--:|
| 漏判（低于标注） | **19** | **0** |
| 误抬（高于标注） | 13 | 15 |

多出的 2 条误抬全部是 **R2b → R3**，即"该就医"被判成"该叫 120"——
是安全方向，代价是多一次语义复核、话术更保守。

> ⚠️ **合并复核时补充的口径提醒**：上表只覆盖 177 条高风险基准。
> 若把关键词兜底作为**所有输入**的下限，低风险池也要算代价：R0/R1 的 1263 条里，
> 关键词兜底本身已把 237 条抬到更高等级（18.8%）。在线档模型如果原本判对，
> 这 237 条会被下限强制抬上去。是否启用，应先用一份**在线档的逐条输出**复测，
> 而不是只看高风险集的漏判清零。

> **这一行改动属于 `orchestrator.py`（组长文件），B 没有改，只出建议。**
