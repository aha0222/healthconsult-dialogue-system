# 项目现状、进度总结与未来方向

> 2026-10-10 整理。仓库 `healthconsult-dialogue-system`，共 74 次提交（2026-07-14 起）。
> 本文只讲文字与数字，配套明细见 `docs/` 下各专题文档。
>
> **档位口径（2026-10-10 更新）**：落地平台（机器人）**是联网的**，所以**在线档是主路径**；
> 本地离线档保留为「断网不中断 + 数据不出户」的可选项，不再投入优化它的速度。
> 本文中所有"本地档"数字都是**可选项**的指标，不是主线指标。

## 一、这个项目是什么

面向**独居/空巢老人**的健康陪伴对话系统「小暖」。核心主张三条：

1. **会看风险（主线）**：老人随口一句话里可能有急症（黑便、突然看不清、摔跤后还能走），
   系统必须识别并明确催就医，而不是单纯安慰。**这是全项目的重心**：三档共用同一套
   三层安全链路，换模型不换安全。
2. **可换档**：主路径走云端；同一套代码也能**以离线档启动**（`OFFLINE_MODE=1`）并在完全
   无网的机器上跑完整个问答。⚠️ **注意是"启动时选档"，不是运行时自动降级** ——
   在线档运行中断网会直接报错（见 §4 缺口 5），不会自动切到本地模型。
3. **规范与代码分离**：回复规范（`skills/`）是纯文本，零 Python；换前端、换后端、换模型都不动规范。

## 二、系统构成

```
前端 frontend/  ──HTTP/SSE──▶  后端 backend/  ──system prompt──▶  skills/（SKILL.md + 规则 + 语料）
   │                              │ 三层安全 + 对话编排
   │ HTTP 直连 8100                │ get_llm()：云端 DeepSeek ／ 本地离线（OFFLINE_MODE）
   ▼                              ▼
voice_service/（ASR/TTS/流式/打断）    本地 LLM 端点（llama.cpp）或任意私有端点
```

| 模块 | 规模 | 状态 |
|------|------|------|
| `backend/` 对话编排、三层安全、API、SQLite | 61 文件 / 10294 行 | 可用 |
| `frontend/` 人格展示 + 在线对话 + 语音接线 | 11 文件 / 4921 行 | 可用 |
| `voice_service/` ASR + TTS + 流式/打断 | 12 文件 / 1850 行 | 可用 |
| `tools/` 语料生成/质检/评测/离线自检 | 41 文件 / 9443 行 | 可用 |
| `skills/` 回复规范包（纯规范，零 Python） | 语料 v0.4.0 共 1725 条 | 可用 |
| `scripts/offline/` 一键冷启动 / 打包 / 拔网线自检 | — | 可用 |

**能力开关（默认全关，与上一阶段行为完全一致）**：`VOICE_ENABLED`、`OFFLINE_MODE`、
`SPEAKER_DETECT_ENABLED`。

## 三、已完成的工作

### 3.1 对话内核

- **双维度分类**：24 个场景（7 组）× 5 档风险（R3 / R2b / R2a / R1 / R0），LLM 在回复末尾输出
  `[RISK:x]` + `[SCENE:x]` 标记，小模型漏标时由本地关键词兜底。
- **检索增强**：关键词快路径（0 token）预判风险场景，非高风险时检索相似语料注入 prompt。
- **4 种人格**：温婉邻居型（默认）/ 贴心闺女型 / 素朴家常型 / 从容守护型，附复现式选型评测。

### 3.2 三层安全（任何模型、任何开关状态下都不放松）

| 层 | 做什么 | 失效时的后果 |
|----|--------|--------------|
| 1. SKILL.md 提示层 | 教会模型怎么识别与催就医 | 小模型会整层失效（实测 3B 无标签、无 120 提示） |
| 2. 关键词红线 `safety_checker.py` | 快路径兜底，识别急症表述 | 覆盖率高但有漏检（见 §4.2） |
| 3. LLM 语义复核 | 高风险再调一次模型复核 | 离线档把复核范围放宽到**全等级**，代价是每轮多一次推理 |

红队回归集 **56 例**随 CI 执行；新增安全规则必须补用例。曾修复「中风后康复 vs 中风现症」误判
（`strip_past_events()`）。

### 3.3 语音

- **ASR**：本地中文识别（Paraformer）；**TTS**：Kokoro v1.1-zh（GPU 优先，sherpa-onnx 回退）。
- 中文 TTS 已换到 **v1.1-zh / 音色 `zf_001`**，实测实时率 **0.023**，并补齐三处：多音字修正表
  （觉/着/得/教/干/长等 200+ 处误读）、数字间斜杠（`150/95` 读「一百五十比九十五」）、
  正文里的英文缩写（`维生素D`→「地」）；长句减速默认开启（时长代价 +0.6%）。
- 播放侧：逐句队列 + 预取 + 随意打断，LRU 缓存重听秒出。

### 3.4 说话人识别

区分「老人本人 / 家属」，只调整称呼与内容侧重，**不放松任何安全红线**；低置信一律按老人处理。

- 评测集 **163 角色用例**（0 基线 67 / 引用转述 24 / 无称呼可判 12 / 无称呼模糊 12 / 双人对话 16 /
  方言口语 20 / 历史延续 12）+ 12 条安全不变式。
- 基线 85.9%，定位三个根因（方言亲属称谓、引号内转述、自称症状被误判为家属）后修到
  **163/163，误切家属 0**（误切是唯一会伤害老人体验的方向，门槛硬设为 0）。

### 3.6 运行档位（**2026-10-10 起：在线为主，离线为可选降级档**）

落地平台（机器人）**是联网的**，所以主路径走云端；离线档保留为「数据不出户 / 长期无网」
场景的**可选启动档**，不再投入优化它的速度。三档实测（同一套 `risk_cases.jsonl` 与真实 system prompt）：

| | **在线档（主）** deepseek-flash | 7B/GPU 本地 | 3B/CPU 本地 |
|---|---|---|---|
| 端到端一轮（含检索与语义复核） | 未单独测（单条调用 **1.6 s**） | 5.3 s | 276 / 284 s |
| RISK 标记**输出率** | **95%**（37/39） | 90%（27/30） | **7%**（2/29） |
| RISK 标记**正确率** | **87%**（34/39） | 73%（22/30） | 3%（1/29） |
| SCENE 与期望有交集 | **74%**（29/39） | — | — |
| 拔网线自检 `offline_check.py` | — | 11/11 | 11/11 |

> 结论：**在线档的标签可信度（95% / 87%）与本地 7B（90% / 73%）、3B（7% / 3%）不是一个量级**，
> 这也是「在线为主」最直接的依据。三档的样例数不同（39 / 30 / 29），绝对值只作档位间比较。
> 在线档最弱的一项是 **SCENE 74%**，说明检索与提示词还有空间。
> 复现：`.venv/Scripts/python.exe -X utf8 tools/offline_tag_rate.py --online --n 39`

本地档延迟的数次差来自**前缀缓存是否命中**（系统提示词约 7–10k token，命中与否差一倍以上）。

**交付档最值得记住的一条**（离线降级时的价值证明）：把急症输入喂给 3B，原始回复是一段安抚话、
**既无标签也无 120**；经完整后端（关键词 + 语义复核）后 `fallback_used=True`，最终回复变成
「您现在的症状像是急症，不能在家等。**请马上打 120**…」。也就是说**三档共用同一套后端安全链路**，
换档不换安全。

7B + Kokoro 显存共存实测 7073 / 8151 MiB；全链路彩排（含语音）一轮 10.0 s + TTS 1.6 s，
期间三个服务零非本机连接。

## 四、当前的缺口与风险（如实列出）

| # | 问题 | 影响 | 现状 |
|---|------|------|------|
| 1 | **隐私：主路径把健康对话发到云端** | 与「数据不出户」的卖点冲突；需授权与合规口径 | **当前第一优先**，见 §6 议题 1 |
| 2 | **在线档 SCENE 标记只有 74%** | 场景判错会走错回复路线（不是安全问题，是体验问题） | 检索与提示词有空间 |
| 3 | **关键词兜底会低估 42% 高风险样本**（75/177，如「一只眼睛突然看不见」R2b→R0） | 被误判成低风险的高危输入会整层跳过语义复核 | 靠"语义复核放宽到全等级"兜住；根因在关键词表，需扩表 |
| 4 | **在线档成本与限流未评估** | 联网后按量计费，长会话（SUMMARY 摘要）会放大调用 | 尚未测 |
| 5 | **在线档断网不会自动降级** | 网一断，云端调用直接失败并报错给老人 —— **没有**自动切到本地档 | 档位是**启动时**按 `OFFLINE_MODE` 静态选的（`get_llm()`），运行时不切换。需补：启动探测 + 运行时切换 + 提示文案 |
| 6 | **紧急通知家属只有设计、无实现** | 唯一「主动对外发消息」的能力，风险最高 | 有意压着不做 |
| 7 | **未做真实用户试点** | 无真实老人使用数据，误报/漏报率只有离线评测 | 需先解决数据授权 |
| 8 | 端点楔子残余偶发、交付包不含 GPU 资产 | 影响离线可选档，不再阻塞主线 | 首请求 502 已修；其余降级为低优先 |

> 提前作废的两条：**「交付档 4.6 分钟跑不动实时对话」与「3B 标签只有 7%」**
> **不再是阻塞项** —— 既然机器人联网，主路径走云端，这两个问题只影响"可选降级档"的质量。

**演示注意（踩过）**：① 首次合成多约 6 秒（加载 330MB 权重），开场前先热一句；
② 本地 7B 对「血压 150/95 高不高」四次采样中**有一次**答成「还在正常范围内」 ——
温度采样波动，避免临场即兴问具体数值（在线档未复现此问题，但同样建议避开）。

## 五、未来发展方向

### 5.1 近期（中期检查前，约 1 周）

1. **把主线拉回在线档**：补一组在线档的端到端指标（延迟/成本/限流），并把每次调用量记下来
   （现在只有一个"单条 1.6 s"）。**这是最该先做的一条** —— 主路径反而没有实测数据。
2. **在线档断网要有优雅降级**：现在网一断就报错（档位是启动时静态选的）。至少要做到
   「探测到云端不可用 → 提示 + 切本地档继续」，而不是把错误抛给老人。
3. **实拔网线确认**（降级为次要）：离线作为可选档，值得 30 秒闭环一次 —— 它现在是
   「数据不出户 / 无网可用」的证据，不再是主线卖点。注意：**要拔网线得先用离线档启动**
   （`start.ps1 -Gpu`），在线档拔线只会报错。
4. **演示脚本**：已完成 —— 见 `docs/midterm_review_runbook.md`（提纲 + 实测过的问题 + Q&A +
   现场预案 + 口播稿）。
5. **汇报材料**：本文 + 专题报告可整合成一份 docx。

### 5.2 中期（第四阶段，约 3–5 周）

按优先级（已按"在线为主"重排，**离线降速类工作全部降级**）：

1. **隐私与数据授权的口径**（最高优先，这不是技术活而是先想清楚的问题）。主路径联网后，
   健康对话会离开本机 —— 与"数据不出户"的卖点直接冲突。要定：哪些数据可以出网、
   是否脱敏、老人/家属如何授权、留痕到什么程度。**这个问题不解决，其他都白做。**
2. **在线档的回复质量与成本**（组长，3–5 人日）。在线档最弱的一项是 SCENE 74%，
   检索与提示词还有空间；同时长会话要靠 `SUMMARY` 摘要控制 token 与费用。
3. **说话人识别加固**（组长，5–8 人日）。评测集从 163 扩到 150–250 的更细分布（引用转述、
   无称呼、一轮两人、模糊）。**待定策略**：模糊时判老人本人（保守）还是反问一句（更稳但多一轮）。
4. **紧急通知家属**（10–15 人日，风险最高）。地基 `alerts.py` 已在。缺四块：数据授权、
   复核闸门（倾向本人同意 + 倒计时）、渠道（短信/电话/企微钉钉）、防扰与审计（冷却去重、
   留痕、一键关）。建议从**演练模式**起步（只发自己人 / 只写日志）观察误报率，默认关闭。
5. ~~离线延迟进 5 秒 / 局域网 14B-32B~~ —— **降级为可选**：主路径既然联网，就不必为了
   离线档的秒数投入人日。局域网部署仍可作为隐私方案保留（代码零改动，`OFFLINE_LLM_ENDPOINT`
   指过去即可），但不排在中期。

### 5.3 长期

1. **老人端载体**：目前是网页；真实落地要机器人瘦终端（已知联网）/ 手机 App / 微信小程序，
   涉及唤醒词、免按键、方言识别。
2. **隐私与授权的工程化**：联网是既定前提，那"数据不出户"就不再是默认卖点 ——
   需要一套可解释的授权与留痕机制，而不是一次性的技术开关。
3. **小规模真实试点**：在没有真实使用数据之前，所有安全指标都是离线评测。试点要先解决
   授权，再观测**误报率**（把老人吓到 / 家属被骚扰）与**漏检率**（真急症没提示）。
4. **评测方法学**：说话人按**错误方向**拆指标（误切家属权重最高）、安全按**漏检方向**拆
   （危急零容忍），而不是只看准确率 —— 这两条已落地成硬门槛，后续新能力沿用同一思路。
