# 离线延迟实测与优化方向（2026-10-07）

> 本文是第 3 天的实测产物，供 B 改 `scripts/offline/start.ps1` 与第 4 天写延迟优化方案使用。
> 所有数字来自本机（i7-13650HX / RTX 5060 Laptop 8GB / 7B Q4）的 `llama.err.log`
> 与三个可复现实验，不是估算。
>
> **数据口径**：本文全部为 **7B / GPU 档**。交付默认档 3B/CPU 的数字见 B 的
> 《离线验收口径确认1.md》，两档不得混用。

## 1. 单轮延迟的构成

从 `scripts/offline/logs/llama.err.log` 统计 13 轮真实对话（每轮 1 次主调用）：

| 组成 | 耗时 | 明细 |
|------|-----:|------|
| 主调用预填充 | **3219 ms** | 7209 token @ 2239 tok/s |
| 主调用解码 | 2743 ms | 122 token @ 45 tok/s |
| 复核调用 | 384 ms | 预填充 211 ms（502 token）+ 解码 173 ms（11 token） |
| **一轮合计** | **约 6.4 s** | 预填充占主调用的 **54%** |

**关键事实：那 3.2 秒每一轮都在重算同一份没有变过的系统提示词。**
`SKILL.md` 实测 11,315 字符 ≈ 7,072 token，正是预填充的主体。日志里每次主调用都是
`kv cache rm [3, end)`——只复用了 3 个 token。

复核调用本身很便宜（384 ms），且它的 `max_tokens=300` 实测只用掉 11 个 token。
**所以复核的问题从来不是自身耗时，而是它挤掉了主对话的前缀缓存。**

## 2. 根因：`--parallel 1` 只有一个 slot

26 次请求**严格交替**：13 次主调用、13 次复核调用。离线档全等级复核
（`SEMANTIC_CHECK_RISKS=R3,R2b,R2a,R1,R0`）意味着几乎每轮都有一次复核调用，
而复核的提示词形状完全不同（约 500 token，不含 SKILL.md），于是它把 slot 里
主对话的 KV 缓存整个覆盖掉。

### 实验一：前缀缓存复用（`E:\dc\scratch\prefix_cache_test.py`）

长提示词 A → 短提示词 B（模拟复核）→ 再发一次 A：

| 配置 | 三次请求的预填充 token 数 | 第二次 A |
|------|--------------------------|---------|
| `--parallel 1` | 3440 → 23 → **3440** | 743 ms（全量重算） |
| `--parallel 2` | 3440 → 26 → **1** | **13 ms**（缓存命中） |

`--parallel 2` 下主对话与复核各占一个 slot，前缀完整保住。

**预期收益：单轮 6.4 s → 约 3.2 s。**

## 3. ⚠️ 改 `--parallel` 必须同时改 `-c`，否则对话会被截断

llama-server 把 `-c` 按 `--parallel` **均分**给每个 slot。实测：

| 启动参数 | 每 slot 上下文（`n_ctx_slot`） | KV 缓存总计 |
|----------|------------------------------:|------------:|
| `--parallel 1 -c 16384` | **16384** | 476 MiB |
| `--parallel 2 -c 16384` | **8192** ← 减半 | 476 MiB |

主调用本身就占约 7,200 token，8192 每 slot 几乎没有余量留给历史与回复。

**推荐参数：`--parallel 2 -c 24576`** → 每 slot 12288 token。
7B 是 GQA，KV 很小（16384 token 仅 476 MiB），所以每 slot 12288 时 KV 总计约
714 MiB，代价可接受。若要保守些，`-c 32768`（每 slot 16384，与现状一致）也可行。

## 4. 显存共存（7B + Kokoro GPU）

### 实验二：`E:\dc\scratch\vram_coexist_test.py`

| 配置 | 7B 全层上载 | + Kokoro GPU 后端 | 8GB 内余量 |
|------|-----------:|------------------:|-----------:|
| `--parallel 1 -c 16384` | 6444 MiB | **7023 MiB** | 1128 MiB |
| `--parallel 2 -c 16384` | 5832 MiB | **6607 MiB** | 1544 MiB |

**结论：7B 全层 + Kokoro GPU 共存没有 OOM，也不会静默退化到共享显存**
（Windows WDDM 会溢出到共享显存但不报错，只变慢——这次没有触发）。

配套注意：

- `llama.cpp` 日志确认 `offloading 28 repeating layers to GPU`（+ 输出层 = 全部）。
- 桌面自身占 **693–1356 MiB**，浮动很大。演示前务必关掉浏览器等程序，
  否则 7023 + 600 就逼近 8151。
- 若演示时仍吃紧，退路是语音后端改用 `kokoro-int8-multi-lang-v1_1`
  （sherpa-onnx，CPU，206 MB，已在本地），功能不损、语音延迟略增。

## 5. 优化方向（按收益／确定度排序）

| # | 方向 | 预期收益 | 状态 |
|---|------|---------:|------|
| 1 | `--parallel 2 -c 24576`，让复核不再挤掉主对话前缀缓存 | **省约 3.2 s/轮（54%）** | **实验已验证**，待改 `start.ps1` |
| 2 | 启动时用同一份 system prompt 发一次预热请求 | 消掉服务重启后首轮的预填充 | 未做，`start.ps1` 现只等 `/health` |
| 3 | 提示词里明确要求简短（回复实测 63–224 token，均值 122；224 token 那轮光解码就 5.0 s） | 长尾轮省 2 s 以上 | 未做，需重跑语料/听感验收 |
| 4 | 投机解码，Qwen2.5-0.5B 作草稿模型（同族 tokenizer） | 解码 45 tok/s → 约 1.5–2.5× | 仅 GPU 档有意义，未做 |

**已用实测排除的方向**：

- 压复核的 `max_tokens`：实测只用 11 token，收益为零。
- `-ub` / `-fa` 调参：预填充已是 2048 分块、2239 tok/s，无明显欠配；
  `-fa on` 的价值主要是省 KV 显存（给方向 1 的第 2 个 slot 腾空间），速度收益有限。
- 换更小的模型：标签输出率本就不达标，会更差。
- 流式：后端整段复核通过才发出，离线档全等级复核没有可流式的轮次；
  要开必须重谈安全时序。建议只记录。

## 6. 对第 4 天交付的影响

原计划第 4 天 B 的交付是「延迟表 + 进入 5 秒的路径」，并预设了"连续对话不新建会话，
只有首句慢"。**按本次实测，这个前提现在不成立**：每一轮主调用都在全量重算，
"热轮"并没有热起来。

修完方向 1 之后才是真的热轮。所以第 4 天的交付重点应改为：

1. 方向 1 落地并复测（应有 3B/CPU 与 7B/GPU 两档数据）；
2. 再谈"进入 5 秒"——**7B/GPU 档：3.2 s，已达标**；
3. 3B/CPU 档：预填充 64 tok/s，那份 7,209 token 的重复预填充约合 **112 秒/轮**，
   这正是 B 日志里那些 95–125 秒条目的更合理解释（可能不是"冷轮"，而是
   **每一轮丢了缓存**）。建议 B 用同一口径重读自己的日志再下结论。
