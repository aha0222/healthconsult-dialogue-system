# 语音合成换成 Kokoro v1.1-zh：改动、实测与待定项

> 2026-10-09。把线上中文 TTS 从 v1.0 的 `zf_xiaoxiao` 换成 v1.1-zh 的 `zf_001`。
> 同批语料两版音频、试听页、复现命令见文末。

## 1. 一句话结论

v1.1-zh 是专训普通话的版本（韵律更贴中文），换过去**不影响**我们自写的多音字修正表
和数字规则；但它是**并行版本不是升级版**——官方 README 明说「drops many voices」，
并且有两个必须先补的坑（数字间斜杠、正文里的英文缩写）。三项都已处理。

## 2. 改了什么

| 文件 | 改动 |
|------|------|
| `voice_service/tts.py` | `KOKORO_TORCH_REPO` → `hexgrad/Kokoro-82M-v1.1-zh`；`KOKORO_TORCH_VOICE` → `zf_001` |
| `voice_service/tts.py` | 新增 `_kokoro_en_callable()`：接一条**无模型**的英文管线，给正文里的英文片段做音素化（v1.1 官方做法） |
| `voice_service/tts.py` | 新增 `_slow_speed()`：长句减速回调（官方 make_zh.py 曲线），默认启用，见 §3.1 |
| `voice_service/tts.py` | `normalize_for_tts` / `split_sentences` 增加 `convert_numbers` 开关（默认开，行为不变），供 A/B 对比用 |
| `voice_service/tts.py` | 新增数字间斜杠规则：`150/95` → `一百五十比九十五` |

### 2.1 v1.1 会踩的两个坑

**坑一：数字间的斜杠。** 血压惯写 `150/95`。原样交给 G2P，v1.0 和 v1.1 都走
`cn2an`，按**分数**读成「九十五分之一百五十」——意思反了。我们自写的数字规则能读对
数字，但斜杠会变成 G2P 的未知音素 `❓`（只出声不出字）。现在在数字改写前先把
「数字/数字」换成「比」，两条链路都读成「一百五十比九十五」。

**坑二：正文里的英文缩写。** v1.1 的中文前端把非中文片段**一律**换成未知音素，
`维生素D`、`做个CT` 会没声音。实测语料 2239 条正文里 1.03%（23 条）含拉丁字母
（维生素D/B12、CT、APP、TSH）。官方 `make_zh.py` 的做法是传 `en_callable` 给
`KPipeline`，把英文交给同一模型。已照做：`做个CT看看` → `…sˌitˈi 看看`，
`维生素D` → `dˈi`。

> ⚠️ `en_callable` 内部用 spaCy，**缺 `en_core_web_sm` 时 misaki 会当场 `pip install`**。
> 离线机器上那是一次必然失败的网络调用。已在建管线前自查，缺了就跳过并打 WARNING
> （中文照常，只是英文没声），不会触发下载。离线机需预装：`python -m spacy download en_core_web_sm`。

### 2.2 没动的、以及为什么

- **多音字修正表（`pronunciation.py`）不用改。** v1.1 的前端 `_init_pypinyin()` 会
  重载 pypinyin 大词典（`large_pinyin.load()`），一度担心把我们的单字默认音冲掉。
  实测两种注入顺序结果一致，且不注入时确实是错的——修正表在 v1.1 下**照样生效**：

  | 词 | 不注入 | 注入后 |
  |----|--------|--------|
  | 睡个好觉 | shui4 ge4 hao3 **jue2** | …**jiao4** ✅ |
  | 长时间 | **zhang3** shi2 jian1 | **chang2** … ✅ |
  | 睡不着 | shui4 bu4 **zhe5** | … **zhao2** ✅ |
  | 口干 | kou3 **gan4** | kou3 **gan1** ✅ |
  | 教您做操 | **jiao4** nin2 … | **jiao1** … ✅ |
  | 地高辛 | **de5** gao1 xin1 | **di4** … ✅ |

- **自写的数字规则（`_number_to_cn`）保留，不撤。** 原计划是撤掉、交给 cn2an。
  实测 cn2an 会把 `150/95` 读成分数，**语义读反**；自写规则读数字是对的。
  两者都要：规则读数字 + 新增的「比」处理斜杠。`convert_numbers=False` 的分支
  留在代码里，供以后复核用。

## 3. 实测数据（RTX 5060 Laptop，GPU 档）

- 权重 314MB，hf-mirror 拉到本地 35 秒（`config.json` + `.pth` + 4 个音色）。
- 合成实时率：**RT ≈ 0.023**（5 秒音频 ≈ 0.12 秒墙钟）。整段 54 秒的回复（一轮
  真实问答的全文）1.6 秒合成完。
- 冷启动：首次合成多约 **6 秒**（加载 330MB 权重 + 建前端）。演示前应先热一次。
- 显存共存：7B（4168 MiB）+ Kokoro + 桌面 ≈ **7073 / 8151 MiB**，够用。

### 3.1 语速与「长句赶」

v1.1-zh 训练数据基本在 100 token 以内，长输入会**越往后越赶**。按 app 的切句规则
（≤45 字一个合成单元）统计 300 条真实回复共 3313 个单元：

| 音素数 | 占比 |
|--------|------|
| 中位 45 / 均值 55 / 最大 149 | — |
| > 83（官方减速曲线起点） | 24.1% |
| > 120 | 6.4% |
| > 183（官方曲线下限） | 0.0% |

官方 `make_zh.py` 给了一条按音素数递减语速的曲线（`speed_callable`）。在我们的
app 上：短单元（≤83 音素）**没区别**；44 字整句一次合成的那种能慢 **7%**
（7.09s → 7.59s）。

**代价实测（决定默认启用的依据）**：12 条语料 68.6s → 69.4s（+1.2%），但那份样本
长句偏少；改用 6 条真实长回复（250～282 字）重测，**408.2s → 410.5s（+0.6%），
每条约 +0.4 秒**，合成墙钟无变化。首句通常很短、不命中曲线，所以「多久听到第一声」
不受影响，只有长句的尾巴慢下来。结论：**默认启用**。

## 4. 已定（2026-10-10，组长听完 A/B 后拍板）

1. **音色 = `zf_001`**（B 版）。备选里 `zf_002`/`zf_003` 音高低约 40Hz、语速慢 15%～18%，
   同内容总时长多 4～6 秒；选 B 是音色与语速的综合平衡。
2. **长句减速 = 启用**（F 版）。听感上长句尾巴更自然；代价实测每条约 +0.4 秒（+0.6%），
   首声延迟不变，见 §3.1。
3. **英文缩写念法 = 接受**（`CT` → 「西提」、`维生素D` → 「地」）。比没声音好；
   正文里含拉丁字母的只占 1%。

E=`zf_001` 不转数字 / F=`zf_001` + 长句减速。
