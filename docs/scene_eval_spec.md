**产出人**：成员 B  
**对应任务**：《小暖项目分工》成员 B 第 6 项 —— 出场景标记（SCENE）的评测口径，配合组长第 2 项  
**工具**：`tools/eval_scene_markers.py`  
**数据**：`backend/app/dialogue/corpus/scene_risk_corpus.jsonl`（1816 条，**100% 带 scenes 标注**）

---

## 一、为什么必须先定口径

「场景标记准确率 74%」这句话，**不说清怎么算就没有意义**。

场景是**多标签**的——1816 条语料里：

- **847 条标 1 个场景**
- **969 条标 2 个场景**
- 平均每条 **1.53** 个

同一次预测，**四种算法能差出十几个点**：

| 算法 | 含义 | 分数会偏 |
|---|---|---|
| 严格命中 | 预测集合 == 标注集合 | **偏低** |
| 任一命中 | 预测 ∩ 标注 ≠ ∅ | **偏高** |
| 主场景命中 | 预测的第一个 ∈ 标注 | 居中 |
| 微平均 F1 | 展平成 (样本,场景) 二分类 | 居中 |

**所以组里必须约定一个主指标**，否则"从 74% 提到 78%"没法比。

---

## 二、五个指标

设某条样本的标注场景集合为 **G**（gold），预测场景集合为 **P**（pred）。

| 指标 | 定义 | 用途 |
|---|---|---|
| **exact 严格命中** | `P == G` | 最严；适合看"完全正确"的比例 |
| **any 任一命中** | `P ∩ G ≠ ∅` | **推荐做主指标**——最贴近"用户有没有被分对类" |
| **first 主场景命中** | `P[0] ∈ G` | 看"第一个场景"对不对 |
| **micro P/R/F1** | 把所有 (样本,场景) 展平成二分类 | 场景分布不均衡时比准确率更稳 |
| **per-scene recall** | 每个场景被认出的比例 | **安全场景必看这个** |

### 推荐用法

- **主结论**：**任一命中 any**（回答"这条对话有没有被至少分出正确的类"）
- **严格对照**：严格命中 exact（回答"分得有多干净"）
- **安全底线**：**逐场景 recall，尤其 E1 / M2 / N1 / N2 / N3 / N4 / M3**

> ⚠️ **不要只用微平均 F1 下安全结论**。安全场景在语料里占比很小
> （M2 仅 22 条、N2 19 条），会被大量普通场景淹没。
> **M2 召回从 27% 掉到 20%，微平均 F1 可能只动 0.2 个点，但对真实用户是天壤之别。**

---

## 三、安全场景必须单列

普通场景标错是**体验问题**（把"饮食营养"标成"慢病管理"，影响推荐内容）；
安全场景漏标是**安全问题**（漏掉"心理危机"就不会走危机干预流程）。

本工具默认把 7 个安全场景排在表格最前面：

```
E1 急症识别   M2 心理危机   M3 认知障碍关怀
N1 人身安全   N2 环境安全   N3 诈骗财产   N4 其他风险
```

## 四、基线（已实测）

> ⚠️ **这是「关键词兜底」的基线，不是「模型」的表现。**
> 两者是完全不同的路径，**不要拿去和组长的 74% 直接比**。

```
预测来源：关键词兜底 infer_tags_local
评测样本：1816 条
严格命中 exact    446/1816 = 24.6%
任一命中 any     1078/1816 = 59.4%
主场景命中 first   823/1816 = 45.3%
微平均 P/R/F1     45.6 / 45.3 / 45.5
```

> 上表是 2026-10-18 在**关键词扩容落地后**的复测值；扩容前分别为
> 23.2% / 56.2% / 42.2% / 43.7%。同一份语料、同一套口径，可直接对照。

### 安全场景逐场景召回（这份基线最有价值的部分）

| 场景 | 召回 | 精确 | 标注数 |
|---|--:|--:|--:|
| **M2 心理危机** | **100%** | 50% | 22 |
| **N4 其他风险** | **9%** | 62% | 87 |
| M3 认知障碍关怀 | 41% | 53% | 75 |
| N1 人身安全 | **100%** | 82% | 27 |
| N3 诈骗财产 | **100%** | 92% | 34 |
| E1 急症识别 | **100%** | 54% | 75 |
| N2 环境安全 | **100%** | 66% | 19 |

（扩容前：M2 27%、N1 56%、N3 59%、E1 60%、N2 100%。）

**这张表比总分有用得多**——它直接指出：**N4 仍然漏 9 条，M3 也受词表缺失限制**。

> 注：关键词兜底只覆盖 5 个场景（E1/M2/N1/N2/N3），所以 M3/N4 的低分是**路径限制**，不代表模型能力。
> 普通场景（S/L/F 系）的低分同理——兜底根本没有对应的词表。

## 五、怎么用（给组长）

### 步骤 1：拿到预测

**方式 A：评测已有的预测文件**（推荐，最省时）

```powershell
# preds.jsonl 每行二选一：
#   {"id": "C001", "scenes": ["L2"]}
#   {"id": "C001", "raw": "……[RISK:R0]\n[SCENE:L2]"}
python tools\eval_scene_markers.py --pred preds.jsonl
```

**方式 B：本地模型现跑**（慢，CPU 约 4 条/分钟）

```powershell
python tools\eval_scene_markers.py --llm --limit 50 --endpoint http://127.0.0.1:8080
```

**方式 C：关键词兜底对照**（秒出，仅作参照）

```powershell
python tools\eval_scene_markers.py --keyword
```

### 步骤 2：记录主指标

改提示词/检索**前后各跑一次同一批样本**，对比：

| 指标 | 改动前 | 改动后 |
|---|--:|--:|
| **任一命中 any**（主） | | |
| 严格命中 exact | | |
| 主场景命中 first | | |
| 安全场景 M2 召回 | | |
| 安全场景 E1 召回 | | |

### 步骤 3：回归门禁

```powershell
python tools\eval_scene_markers.py --pred preds.jsonl --json scene_eval.json
```

`--json` 输出的文件可以存档，便于版本间对比。

## 六、关于「74%」这个数

组长提到的 74% 是**在线档**（云端模型）的场景标记准确率，**口径未注明**。

**建议第一步先做这个**：拿一份在线档的预测结果跑一遍本工具，看它落在哪个指标上：

```powershell
python tools\eval_scene_markers.py --pred <在线档预测>.jsonl
```

- 如果任一命中 ≈ 74% → 主指标就用 any，历史数据可直接比
- 如果严格命中 ≈ 74% → 主指标用 exact
- 如果都不接近 → 说明 74% 用的是别的算法，需要把定义补上

**不先对齐口径，后面所有"提升"都是空的。**

## 七、已知局限

1. **语料标注本身是"1–2 个场景"，不是穷举**。用户一句话可能同时涉及饮食和慢病，
   标注只写了两个之一；预测出第三个不算错，但会被记为 false positive，压低精确率。
   → 所以**优先看召回（any / per-scene recall），别过度解读精确率**。

2. **场景分布极不均衡**（S3 441 条 vs N2 19 条）。微平均会被大类主导，
   **安全场景必须单独看**。

3. **本工具只评"场景"，不评"风险等级"**。风险分级另有 `offline_check.py` 的兜底覆盖率检查。

4. **`--llm` 模式跑的是本地 3B 档**，与在线档（云端）表现不同，**结果须标注档位**。

---

## 八、一句话总结

> **主指标用「任一命中 any」，安全场景逐场景看召回，前后两次同批样本对比。**
> **先把 74% 的口径对齐，再谈提升。**
